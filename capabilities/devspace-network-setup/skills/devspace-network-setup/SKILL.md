# DevSpace Ultra network setup

Use this Skill when the user asks to install, set up, upgrade, reconnect, publish, expose, or repair DevSpace Ultra, Local Gateway, DuckDNS/DDNS, Caddy, Cloudflare tunnel, OAuth, router forwarding, or the public MCP URL.

## Operating principle

Work as an installation guide **and** local executor:

- Execute every safe local inspection and setup command yourself through DevSpace workspace/shell tools.
- Ask the user to act only for account ownership, masked secret entry, router administration, ISP/CGNAT decisions, or a browser authorization screen that should remain under the user's control.
- After each user action, re-run a concrete verification. Never accept “I clicked it” as proof by itself.
- Keep the existing Local Gateway state and OAuth data unless a migration gate proves replacement is safe.
- Do not restart an unrelated application runtime such as Blender while repairing network ingress.

## Route decision

Choose exactly one route from current evidence:

1. **DuckDNS/DDNS + Caddy — preferred**
   - The machine has a publicly routable IPv4/IPv6 address.
   - The user can forward TCP 80 and 443 on the router.
   - A stable DuckDNS hostname can point to the current WAN address.
2. **Cloudflare named tunnel — fallback**
   - The ISP uses CGNAT, router forwarding is unavailable, or the user cannot expose 80/443.
   - Use a stable named tunnel and hostname, not a temporary Quick Tunnel.
   - State clearly that any Worker relay in the path is governed by the selected Workers plan and its current request allowance.
3. **Local only — diagnostics**
   - Suitable for backend development only; it is not a public ChatGPT MCP endpoint.

Do not pick Cloudflare merely because it is easier. Diagnose the direct route first.

## Phase 1 — inspect without changing state

1. Open the installed DevSpace package workspace.
2. Read `package.json`, `install.ps1`, `scripts/devspace-ultra-setup.ps1`, and `scripts/devspace-local-ingress.ps1` from the installed version.
3. Run syntax/static setup gates before executing the installer.
4. Read current config and health without printing secret values:
   - Gateway `http://127.0.0.1:7678/healthz`
   - active Core memory endpoint on 7688/7689
   - Scheduled Task state
   - current public base URL and ingress mode
5. Inspect WAN/public-address evidence and compare it with the router's WAN address when available. A private or carrier-grade WAN address is a CGNAT warning.
6. Inspect listeners and port ownership. Gateway/Core and application MCP ports must remain loopback-only.

Write one natural-language progress report after this meaningful medium-sized setup phase if it produced a useful route decision or blocker.

## Phase 2 — prepare credentials safely

Never ask the user to paste a DuckDNS token or Cloudflare tunnel token into normal chat.

Preferred methods, in order:

1. Let the signed setup script show a masked `Read-Host -AsSecureString` prompt.
2. For unattended setup, ask the user to set a **process-scoped** environment variable directly in their own PowerShell window, then remove it immediately after installation.
3. Persist only the DPAPI-protected secret generated by the setup script.

Reject any workflow that places a secret in:

- a command-line argument;
- `config.json`;
- Task Scheduler arguments;
- a Git-tracked file;
- a log or progress report;
- a generated status JSON;
- the conversation transcript.

## Phase 3A — DuckDNS/DDNS + Caddy

Use the tagged one-command installer whenever possible:

```powershell
$p=Join-Path $env:TEMP 'devspace-ultra-install.ps1'
iwr https://raw.githubusercontent.com/enwong93-sketch/devspace-ultra/v0.5.2/install.ps1 -OutFile $p
& $p -Network DuckDNS
```

Before execution:

1. Verify the downloaded script or release checksum when the environment is sensitive.
2. Confirm the user controls the selected DuckDNS hostname.
3. Confirm TCP 80 and 443 can be forwarded to this computer.

The Agent may execute local setup, Scheduled Task creation, Caddy installation/configuration, Windows Firewall rules, Gateway health checks, and certificate/public endpoint tests. The user must perform or approve:

- creating/selecting the DuckDNS subdomain in their account;
- masked token entry;
- router login and port-forwarding changes;
- any ISP-side configuration.

Guide router forwarding one field at a time:

- protocol: TCP;
- external ports: 80 and 443;
- internal host: the DevSpace computer's stable LAN address;
- internal ports: 80 and 443;
- avoid exposing 7678, 7688, 7689, Blender ports, or other MCP application ports directly.

After the user saves the router rule, verify from outside the LAN when possible. A local loopback success is not proof of public reachability.

## Phase 3B — Cloudflare fallback

Use only when direct DDNS ingress is unavailable or rejected by evidence.

```powershell
$p=Join-Path $env:TEMP 'devspace-ultra-install.ps1'
iwr https://raw.githubusercontent.com/enwong93-sketch/devspace-ultra/v0.5.2/install.ps1 -OutFile $p
& $p -Network Cloudflare -PublicHostname 'devspace.example.com'
```

The user controls Cloudflare account authorization, DNS/tunnel creation, and masked token entry. The Agent handles local `cloudflared` installation, DPAPI secret storage, Scheduled Task setup, and health verification.

Use a **named tunnel** with a stable hostname routed to `http://127.0.0.1:7678`. Do not use a Quick Tunnel as a production ChatGPT connector URL.

If a Worker relay is used, explain that Worker invocations consume the current plan allowance. Do not quote a stale numerical quota from memory; consult current official Cloudflare limits when the exact allowance matters.

## Phase 4 — authoritative verification

Do not declare success until all applicable checks pass:

1. Scheduled Task is running with no execution-time ceiling.
2. Gateway `/healthz` returns `ok: true`.
3. One Core responds on 7688 or 7689 with:
   - a stable PID;
   - system-managed heap rather than a 512 MB cap;
   - no crash loop;
   - no new OOM/fatal signature.
4. Public HTTPS hostname resolves to the intended route.
5. `/.well-known/oauth-protected-resource/mcp` returns valid metadata.
6. `/mcp` produces the expected OAuth challenge without exposing a bearer token.
7. The ChatGPT connector can initialize, list tools, and execute one harmless read-only tool.
8. Reconnect once and confirm the same conversation can still call tools.
9. Confirm Gateway/Core/Application MCP ports remain loopback-only.
10. Confirm no secret value appears in config, logs, task arguments, Git status, or generated status files.

Write a progress report after the local installation phase, after public ingress verification, and after final ChatGPT connector acceptance when each is a meaningful medium-sized milestone. Do not report every command.

## Failure handling

- Preserve the original config and state before migration.
- If Gateway is healthy but Core is not, keep the Gateway listener alive in degraded mode and diagnose the newest Core startup error only.
- Do not repeatedly reconnect the ChatGPT app while the backend is unhealthy.
- On DuckDNS failure, distinguish DNS update, public routing, port forwarding, Caddy certificate, firewall, and OAuth failures.
- On Cloudflare failure, distinguish tunnel process, DNS route, named-tunnel token, origin health, Worker relay, and plan-limit failures.
- Never erase OAuth/state merely to make a health check green.
- Never use page reload, synthetic user messages, or ChatGPT navigation as a backend recovery substitute.

## Completion report

Return:

- selected route and why;
- stable public MCP URL;
- Gateway/Core health evidence;
- any manual router/account action still outstanding;
- Cloudflare quota caveat when the fallback route is used;
- rollback/backup location;
- confirmation that no secret was printed or committed.
