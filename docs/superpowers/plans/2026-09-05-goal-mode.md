# DevSpace Ultra Goal Mode Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a persistent Codex-style Goal Mode whose ordinary ChatGPT Classic turns each visibly report to the user before a host-supported hidden continuation starts the next assistant turn.

**Architecture:** `GoalRuntime` owns durable Goal/round/continuation state independently from `PlanRuntime`. Model tools mutate Goal state; a dedicated Goal Dock MCP App polls read-only state, atomically claims a continuation lease, calls `window.openai.sendFollowUpMessage`, and acknowledges or releases the lease. The next assistant turn redeems the continuation through `devspace_goal_round_begin`, preventing duplicate round advancement after renderer/network races.

**Tech Stack:** Node.js ESM, `@modelcontextprotocol/ext-apps`, MCP Apps bridge, Zod v4, vanilla HTML/CSS/JS, existing DevSpace fixed MCP server and verification harness.

**Spec:** `docs/superpowers/specs/2026-09-05-goal-mode-design.md`

## Global Constraints

- Goal Mode is separate from Plan Runtime and Context Guardian.
- Every physical Goal turn must produce a complete visible user report before `devspace_goal_turn_report`.
- Automatic continuation must use MCP App `sendFollowUpMessage`, never CDP composer typing.
- Hidden continuation must not create a visible synthetic user message.
- Goal objective and success criteria are immutable in v1; changed final objective means stop old Goal and start a new Goal.
- Active Goal completion requires evidence coverage for every stored success criterion.
- `blocked` requires 3 consecutive same-fingerprint no-progress reported rounds.
- Model cannot arbitrarily pause/stop; `devspace_goal_control` is used by Goal Dock or on explicit user request.
- Chat Swarm workers must not start/mount user-facing Goal Mode.
- Existing `DEVSPACE_WIDGETS=off` behavior and Plan Card behavior must remain unchanged.
- Update `docs/DEVSPACE-ULTRA-HANDOFF-2026-09-05-V0.5-IN-PROGRESS.md` after every independently verified task.

### Task 3: Continuation Lease and Round Redemption

**Files:**
- Modify: `dist/goal-runtime.js`
- Modify: `dist/goal-runtime.test.js`

**Interfaces:**
- Adds: `continuation({ goalId, action, leaseId? })`
- Adds: `roundBegin({ goalId, continuationId }) -> Promise<Goal>`

Continuation `claim` result:

```js
{
  goal,
  claim: {
    goalId,
    round,
    continuationId,
    leaseId,
    expiresAt,
    prompt
  }
}
```

- [ ] **Step 1: RED test exclusive claim**

After an active reported round creates `pending`, first claim must produce one lease and change state to `dispatching`; a second claim before expiry must fail safely without a second lease.

- [ ] **Step 2: RED test release/expiry recovery**

`release` with the current lease returns to `pending`. Advance injected clock beyond `dispatchLeaseMs`; next status/claim normalizes expired `dispatching` back to `pending`.

- [ ] **Step 3: RED test ack and round redemption races**

Require:

- `ack` changes `dispatching -> dispatched`;
- `roundBegin` accepts matching continuation from either `dispatching` or `dispatched`;
- successful round begin increments round exactly once, sets `working`, clears continuation and records `lastConsumedContinuationId`;
- repeated `roundBegin` with the same consumed continuation is idempotent and does not increment again;
- `ack` arriving after `roundBegin` returns an already-consumed/idempotent result instead of failing destructively.

- [ ] **Step 4: RED test dispatched recovery deadline**

If a dispatched continuation never begins a round, advance injected clock beyond `dispatchRecoveryMs`; normalize it back to `pending` conservatively.

- [ ] **Step 5: Implement lease state machine and hidden prompt generator**

The prompt must contain only Goal/continuation IDs, reported round, Goal semantics, and instructions to call `devspace_goal_round_begin` first. It must not include credentials, chain-of-thought or arbitrary raw tool output.

- [ ] **Step 6: Add the full public three-round blocker gate**

After `roundBegin` exists, execute three real reported rounds with the same normalized blocker fingerprint and `meaningfulProgress=false`. Assert count 1 -> 2 -> 3, `markBlocked` rejects before 3 and succeeds after 3; separately prove a meaningful-progress report resets the counter and a changed fingerprint starts a new count at 1.

- [ ] **Step 7: Run runtime tests GREEN**

Expected gate includes:

