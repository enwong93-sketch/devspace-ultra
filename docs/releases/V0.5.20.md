# DevSpace Ultra v0.5.20 — verified start receipts and binding-first state

This candidate fixes a real fresh-Classic Goal initialization failure. The exact
local start-claim registry had validated a page receipt but dropped its
`pageVerified` flag before passing the receipt to the provider binder. It now
preserves that validated proof. Goal and Plan completion bind and recheck the
exact authenticated conversation before creating durable objective state, so a
failed or stale binding cannot create an orphan active Goal or Plan.

Wrong receipts, unverified invocations, stale pages, conflicting provider
identities, wrong OAuth resources and cross-computer authority remain rejected.
Integration tests now exercise the actual registry-to-provider-binder path,
including a page disappearing between binding and live reuse verification.

An active dispatch lease is no longer mislabeled as a stopped or consumed Goal.
Legacy App claim requests delegate to the same backend continuation owner,
rather than acquiring a second competing lease. An ambiguous external delivery
stays quarantined even after expiry; only native branch evidence may reconcile
it. Old falsely superseded rows can record a genuine human-started round, but
that recovery is explicitly classified as manual rather than automatic.

Relay lookup selects the unique exact conversation page instead of an unrelated
first page. Duplicate exact pages, wrong Goal/conversation markers and stale
heartbeats remain rejected. Bounded loopback diagnostics distinguish missing
widgets, missing markers and unavailable follow-up bridges without returning
conversation identifiers or private routing details.

Security preparation updates `fast-uri` to 3.1.8 and `ip-address` to 10.7.2.
The Pi 0.86.1 implementation remains unchanged: a reviewed vendored archive
patches only its shrinkwrap's `brace-expansion` entry to 5.0.12. Root overrides
did not fix a clean installed tree because the upstream shrinkwrap retained
5.0.9, including in Pi 1.0.0. The exact supplier integrity and patch provenance
ship with the archive; fresh installed-tree checks must verify the fix rather
than treating a modified root lock as sufficient.

The loopback catalogue probe follows the current versioned relay resource and
retires only its own session even when a verification assertion fails. It is a
backend probe, not ChatGPT Classic acceptance.

The Goal/Plan advisory tool behavior and continuity work in the v0.5.19
candidate are retained. Native-final-triggered, user-authorized public-message Goal continuation, interrupted-turn
Rescue, repeated Core replacement and exact-package installation/upgrade still
require real-client evidence. Source tests, a healthy Core and manual recovery
must not be presented as that evidence.

Follow-up candidate hardening refuses Core handover while the old Core retains
any background process session, including completed output not yet consumed.
HTTP request drain alone cannot establish that condition: readiness checks the
exact old PID and a validated aggregate session count before candidate startup
and again inside the closed-admission barrier. Missing diagnostics defer the
handover without stopping the Core; a later verified zero count permits retry.
This protects existing work rather than migrating process handles or changing
Goal completion state. Older running Gateways do not gain this guard until
their own reviewed upgrade; source tests do not prove a production deployment.

Tag builds remain **draft-only**, not public stable auto-update targets. Stable
promotion requires the exact archive/source-bound real-client record described
in [continuity acceptance](../CONTINUITY_ACCEPTANCE.md). Respect a physical
desktop-operation stop; do not restart it automatically or change platform or
Computer Use safety instructions to obtain acceptance.
