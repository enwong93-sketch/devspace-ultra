# DevSpace Ultra v0.5.19 — advisory progress and durable Classic tool continuity

This release removes unnecessary Goal, Plan and progress hard blocks from ordinary ChatGPT Classic work. Progress narration remains an Agent responsibility and Goal/Plan state remains backend-authoritative, but a pending or late progress report, an active Plan, or a completed Plan no longer denies reads, edits, commands or the next useful phase. Pending Goal and Plan starts return a structured next action so the Agent can complete the one-time exact-page bootstrap without asking the user to pair the conversation manually.

Classic workspace and Blender calls no longer wait behind a conversation-specific progress claim. The existing `devspace_progress_report` tool once again carries the hidden exact-page relay directly, so an older ChatGPT tool snapshot does not need a newly added `devspace_progress_bind` tool. A pending first report is asynchronous, not a command to stop safe local work; the Agent must still verify the actual card before claiming narration success. Goal, Plan and progress ownership remain exact-conversation scoped, and each computer retains its separate OAuth resource and server instance.

Existing exact local Classic conversations now retain stateful DevSpace tools throughout long work. After the short-lived hidden progress relay is cleaned up, the server revalidates the globally unique hydrated physical conversation page, renews the active capability lease on verified work and recurring progress reports, and preserves the current call fingerprint so a rotated authenticated provider alias can be bound. Reusable host transport sessions select one conversation by exact request trace; a trace collision, wrong Runtime, duplicate page, stale or unhydrated page, mismatched progress-card owner, wrong OAuth resource, another server instance or another computer still fails closed.

Persisted provider-conversation bindings are now scoped to the DevSpace `serverInstanceId`. Legacy unscoped binding state is reset once and must be re-established from an exact local page. This keeps one cloud ChatGPT account usable across independent DevSpace installations without allowing one computer or Connector to borrow another installation's authority.

Release acceptance requires a real local ChatGPT Classic sequence—not only a cloud branch or one successful `open_workspace` call—including repeated stateful tools after the relay-retention boundary and continued access during a long-running exact conversation. Auto-update should be re-enabled only after the installed stable payload passes that physical UI acceptance.
